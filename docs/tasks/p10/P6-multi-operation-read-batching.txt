TASK: Phase 10 / P6 — Multi-operation read batching

MODEL / REASONING / USAGE
- Recommended configuration: `Sol High`.
- Browser required: no.

VERSIONING
- This prompt's assigned project version is `0.10.6`.

GOAL

Make one Operation-mode provider round efficiently request a bounded set of independent observations and return one normalized continuation result batch.

Read Phase 10 authority, P4/P5 protocol behavior, current tool-call collection/execution, benchmark independent-multi-tool case, duplicate-read/evidence freshness logic.

DESIGN

The provider already may emit multiple tool calls in one completed response.

Define an application-owned operation batch:
- ordered list of provider calls;
- per-call validated execution metadata;
- dependency/effect classification;
- bounded maximum batch width;
- normalized provider results returned together after execution.

This prompt keeps execution sequential.

The optimization target is fewer provider rounds, not faster filesystem operations.

INDEPENDENCE

Do not assume every set of reads is independent.

For P6, support batching provider-proposed replay-safe observations whose arguments do not depend on another call's result.

If dependency cannot be proven from the provider proposal/application state, preserve sequential logical behavior.

RESULT PROJECTION

Return one continuation containing all completed projected results in original provider-call order.

Preserve:
- call IDs;
- tool identities;
- duplicate/no-progress rules;
- mutation epoch semantics;
- per-call failures;
- context accounting;
- replay safety.

OPERATION PROTOCOL

Tune the stable Operation-mode instruction/control frame to encourage bounded independent read sets when they are useful instead of read -> provider -> read -> provider serialization.

Do not force batching when one observation is sufficient.

METRICS

Record batch count, width, successful meaningful actions, and useful action density.

PERMANENT REGRESSIONS

Prove:
- three independent reads can be proposed in one provider round;
- results return in provider-call order;
- one malformed/denied call is attributable and cannot corrupt sibling results;
- dependent or ambiguous calls are not incorrectly grouped;
- duplicate read accounting remains correct;
- context pressure includes the complete result batch.

VALIDATION

Run benchmark `independent-multi-tool-001`, structured/tool-loop/context/recovery tests, fast gate once, typecheck, runner, broad suite, and `git diff --check`.

Classify accept/revise/revert from provider-round reduction and efficacy.

Do not:
- execute batch calls concurrently yet;
- batch mutations/processes/approvals;
- add helper inference.
