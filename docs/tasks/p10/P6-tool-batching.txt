GOAL

Turn multiple tool calls proposed in one completed provider response into an explicit validated batch and return their normalized results in one continuation, while keeping execution sequential in P6 so batching correctness is isolated from concurrency.

REQUIREMENTS

- R1: Introduce an application-owned tool-batch representation for all calls from one completed provider response.
- R2: Validate every batch member independently through canonical ToolRegistry schema/effect/policy paths before execution.
- R3: Preserve original provider call order as the canonical result/projection order.
- R4: Execute P6 batch members sequentially; P6 must not introduce concurrency.
- R5: Mixed success/failure within a batch remains explicit per call and must not fabricate batch-wide success.
- R6: Duplicate/no-progress, tool/stage/run budgets, permission/approval, cancellation, mutation epochs, ambiguous effects, and recovery semantics remain per-call authoritative.
- R7: Mutations/process/external-effect calls remain valid batch members only under their existing sequential semantics; batching does not weaken ordering.
- R8: Send all completed batch results back in one provider continuation rather than creating avoidable model boundaries between independently proposed calls.
- R9: Add Phase 10 metrics for tool batches, batch width, provider tool-selection rounds, and batch compression without changing historical metric meaning.
- R10: Add permanent deterministic tests for all-success, mixed success, malformed call, duplicate read, mutation then dependent call, cancellation, and budget exhaustion inside a sequential batch.
- R11: Run `independent-multi-tool-001` and relevant structured-tool/fast efficacy comparisons against the accepted P5 baseline.
- R12: Append `accept | revise | revert` disposition to the optimization ledger; revert production behavior if batching regresses correctness or increases unnecessary provider rounds.
- R13: Set package version to 0.10.6.

INVARIANTS

- I1: P6 adds no parallel execution.
- I2: Every tool call retains unique canonical lifecycle/effect identity.
- I3: Provider-visible result order is deterministic and follows original call order.
- I4: A batch is not a new permission or transaction boundary.
- I5: No B2/C2 run.
- I6: No root package-lock.json.
