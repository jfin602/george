ROOT FAILURE TO REPRODUCE

The official B2 implementation response requested:
1. existing `package.json` overwrite without `expectedSha256`;
2. `write_file("src/app.js")` while `src/` did not exist;
3. `write_file("src/server.js")`.

The SHA rejection is correct.

The blocking defect is that nested-file target preparation during model-originated mutation recovery-intent construction can throw `Workspace mutation parent must exist.` before normal terminal tool evidence, and George exposes no native directory-creation tool for the model to satisfy that prerequisite.

Do not implement a narrow fixture special case.

BOUNDARY 1 — KEEP SHA AUTHORITY

Do not weaken existing-file mutation safety.

Keep:
- `read_file.sha256` as the provider-visible current-content authority;
- explicit model-supplied `expectedSha256` for existing-file write/patch;
- stale-SHA rejection;
- exact write/patch byte semantics;
- text-framing guards;
- mutation-intent approval rules.

George must not silently read, inject, refresh, or substitute a hash for a model-originated mutation.

Install a deterministic convergence regression:

missing SHA -> bounded tool failure -> provider continuation -> read_file -> explicit returned SHA -> retry -> successful mutation.

Prove no mutation happens before the valid retry.

BOUNDARY 2 — RECOVERABLE PRE-DISPATCH FAILURE

Audit `AgentLoopApplicationService.executeTool()` after schema validation through dispatch.

Fix the smallest production seam so a normal local prerequisite/path/precondition error that:
- occurs before dispatch/side effect; and
- is known to have produced no side effect

returns a bounded terminal `tool.failed` ToolResult for that call.

The B2 missing-parent recovery-intent path must be covered exactly.

Requirements:
- keep `tool.requested`;
- attach execution metadata when known;
- do not emit `tool.started` if dispatch never began;
- return the failure into the existing provider continuation;
- later same-response calls may continue in model order unless an existing legitimate hard-stop rule applies.

Do NOT blanket-catch:
- cancellation;
- task/stage/run-budget exhaustion;
- configuration failures;
- ambiguous/outcome-unknown side effects.

Keep explicit approval/policy denial in its existing denied path.

BOUNDARY 3 — CREATE_DIRECTORY

Add a canonical built-in tool:

`create_directory`

Semantics:
- one required bounded relative workspace directory `path`;
- `workspace_mutation` effect;
- no shell/process/network;
- safely create the requested missing directory chain inside the canonical workspace;
- idempotent success if the requested target is already a real directory;
- reject NUL/absolute/traversal paths;
- reject symlink components/target and escapes;
- reject regular-file/non-directory collisions;
- never delete, replace, move, or rename existing entries.

Use canonical workspace/path code, not duplicated string checks in the application loop.

Do not make `write_file` silently create missing parents. Preserve its current contract.

Prefer conservative replay classification and explicit recovery evidence over blind replay.

BOUNDARY 4 — PERMISSIONS

Integrate `create_directory` through the existing execution-effect/approval architecture.

Standard workspace:
- ordinary mutation approval applies.

Workspace Autonomous:
- qualified in-workspace directory creation may auto-run.

Do not broaden:
- outside-workspace policy;
- network;
- remote mutation;
- browser;
- credentials/environment.

If outside-directory creation is not already supported by the canonical outside-filesystem capability, keep it unavailable.

BOUNDARY 5 — RECOVERY

Extend the bounded recovery intent union for `create_directory` with only safe path metadata.

On reopen:
- canonical requested directory exists as a real in-workspace directory -> confirmed complete;
- it is provably absent -> confirmed incomplete;
- unsafe/colliding/ambiguous observation -> conservative outcome;
- never replay automatically.

Preserve write/patch/process/external/approval/provider-continuation recovery semantics.

BOUNDARY 6 — STRUCTURED TOOL SURFACE

Expose `create_directory` to structured implementation and correction stages.

Do not expose it to INSPECT.

Do not add `run_process` to structured coding merely to create directories.

BOUNDARY 7 — PROGRESS / SAFE EVIDENCE

Project `create_directory` as an editing/workspace mutation with bounded path/result metadata.

No raw provider JSON, file bodies, secrets, or unbounded payloads.

Ensure live trace/tool evidence remains terminal and intelligible for:
- missing SHA;
- missing parent;
- directory creation;
- later successful writes.
