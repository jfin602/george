TASK: Correction 9 / P4 — Production structured task-stack execution

MODEL / REASONING / USAGE
- Recommended configuration: `Sol Medium`.
- Browser required: no.

VERSIONING
- Required unchanged project version: `0.9.10`.

GOAL

Complete the missing Phase 9 production task-stack boundary discovered by P1/P4 planning: George can parse individual Task Prompt v1 files and validate a stack definition, but the production application path does not yet own ordered multi-task execution, durable stack progress, fail-stop behavior, or resume.

Implement that missing application/core boundary now. This is required Phase 9 architecture, not benchmark-only tooling.

Read:
- `BOOT.md`;
- `AGENTS.md`;
- current product/architecture/workflow/stability contracts;
- current Phase 9 structured-task decision/format/qualification authority;
- `docs/tasks/c9-structured-task-convergence/{prompt-assessment,implementation-plan,P1-diagnostic-evidence}.md`;
- exact P1-P3 correction candidate source/tests;
- `src/tasks/`;
- `src/application/structured-task.ts`;
- session/session-store/recovery/event contracts;
- Task/Transcript TUI projections;
- frozen `greenfield-express-v1` and `existing-express-feature-v1` instruments.

Preserve all P1-P3 convergence fixes.

PRODUCTION STACK CONTRACT

Add a provider-independent application-owned structured task-stack execution boundary, using the smallest architecture-compatible design.

Preferred shape:

```text
Task Prompt v1 definitions
        |
        v
validateTaskStack()
        |
        v
canonical StackState
stack identity / ordered tasks / current task / terminal state
        |
        v
StructuredTaskStackApplicationService
        |
        +--> StructuredTaskApplicationService for one task
        |
        +--> fail-stop / durable transition / resume
```

Do not put stack authority in OpenTUI, benchmark code, the LM Studio provider, or a temporary qualification harness.

TASK STACK STATE

Introduce canonical bounded stack state sufficient to represent:
- schema version;
- session/workspace identity;
- stack identity/fingerprint;
- ordered task identities/fingerprints/ordinals;
- per-task status;
- current task ordinal/index;
- completed task history;
- terminal stack outcome;
- blocker/failure summary;
- effective execution-policy expectation as needed;
- enough durable evidence to resume safely.

The exact internal type names may follow existing conventions.

Preserve each individual task's TaskState/evidence. Advancing to P2 must not destroy P1 completion/validation history.

Do not solve this by treating three task definitions as one giant merged TaskState.

STACK VALIDATION

Before the first provider/tool execution:
- parse every structured task;
- run canonical `validateTaskStack`;
- reject mixed stack identity;
- reject invalid ordering/duplicates;
- enforce closeout-last semantics where applicable;
- fail before P1 if any task definition is invalid.

No partial execution of an invalid stack.

EXECUTION

Execute strictly in task ordinal order.

For each task:
1. establish the task as current in StackState;
2. execute through the existing corrected `StructuredTaskApplicationService`;
3. retain its complete canonical TaskState and completion/evidence;
4. advance only if the task reaches the required completed state.

FAIL-STOP

If any task ends:
- failed;
- blocked;
- planning_needed;
- cancelled;
- budget_exhausted;
- or otherwise not truthfully completed,

then:
- terminate the stack immediately;
- do not start later tasks;
- preserve the failing task state/evidence;
- record stack terminal outcome;
- expose the next task as not started rather than skipped-success.

This must be production behavior, not a qualification-script convention.

DURABLE RESUME

Integrate StackState with existing LocalSessionStore/session/recovery rules.

Resume must:
- restore already-completed task history;
- identify the exact current/next task;
- never replay an interrupted/ambiguous mutation/process/provider continuation blindly;
- use Phase 5 reconciliation before resuming an incomplete current task;
- never rerun an already completed task merely because the process restarted;
- retain historical task evidence as history rather than current activity.

If one Session cannot safely hold multiple task histories without schema work, make the smallest deliberate session-schema extension required. Existing taskless/single-task sessions must remain openable.

TASK BOUNDARY / SESSION MODEL

Do not fake stack progression with unrelated ad-hoc sessions unless current architecture proves that is the canonical durable design.

The production stack service must provide one coherent stack-level authority for:
- progress;
- failure;
- resume;
- TUI projection;
- qualification.

Individual task execution may internally use task-scoped state as needed, but stack truth belongs to George.

TUI / PROJECTION

Add presentation-safe stack projection sufficient for the existing Task page/header to render:
- stack ID;
- task list;
- completed/current/not-started status;
- current task/work unit;
- terminal failure/block state.

Do not redesign the TUI in this prompt. Add only the projection/event support required so the existing Phase 9 UI can consume stack state without becoming authoritative.

LIVE-WORK RUNNER

Now build/update the repository-owned qualification runner as a thin consumer of the production stack service.

It must:
- use the production stack executor for `greenfield-express-v1`;
- use the normal single-task structured path for single-task instruments where appropriate;
- keep hidden acceptance outside model-visible workspaces;
- support explicit harness-level dependency installation only with deliberate authorization;
- record raw provider/tool/task/context/sandbox metrics;
- never implement its own task progression logic.

GREENFIELD REGRESSION

Add a deterministic fixture proving:
- full stack validates before P1;
- P1 completed -> P2 may start;
- P1 failure -> P2/P3 receive zero provider calls;
- P2 failure -> P3 receives zero provider calls;
- a completed P1 remains durable after reopen;
- reopen resumes at P2, not P1;
- terminal stack failure remains terminal unless the documented resume/recovery contract explicitly permits continuing the same failed task;
- hidden acceptance is qualifying only after full stack completion.

Preserve:
- current Task Prompt v1 grammar;
- P1-P3 convergence limits/evidence handoff/task-wide budget/direct validation;
- ordinary unstructured chat behavior;
- Workspace Autonomous/Bubblewrap behavior;
- Phase 8 and first Phase 9 historical failures;
- package version `0.9.10`.

Do not:
- retune context;
- add Phase 10 concurrency/batching;
- add helper models;
- broaden permissions/network;
- redesign TUI;
- weaken fail-stop behavior for benchmark convenience.

Required validation:
- focused stack state/service/session/resume tests;
- updated live-work runner deterministic tests;
- existing structured-task/correction tests;
- `node --test test/integration/phase9-qualification.test.ts`;
- affected recovery/session-store tests;
- `npm run typecheck`;
- `npm run test:runner`;
- `git diff --check`;
- no root `package-lock.json`.

Create/update permanent regression coverage for the missing production stack-executor defect.

Do not run the official live qualification in P4; P5 owns live evidence.

If implementing production stack authority would require changing the approved Task Prompt v1 syntax, permission ceiling, or canonical recovery laws, return `Planning needed`. Do not return Planning needed merely because the stack executor was previously missing; filling that boundary is the purpose of this prompt.
