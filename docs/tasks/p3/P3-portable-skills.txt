TASK: Phase 3 / P3 — Portable skill registry and turn-scoped activation

MODEL / REASONING / USAGE
- Recommended configuration: `Terra High`.
- Browser required: no.

VERSIONING
- This prompt's assigned project version is `0.3.3`.

GOAL

Add George's first declarative portable skill substrate on top of the qualified P1/P2 context machinery.

Read Phase-3 authority/assessment/plan and inspect exact current context/application/config tests before editing.

Implement a provider-independent skill registry with deterministic discovery from:
- a built-in George skill root;
- a user-global George skill root;
- workspace `.george/skills/`.

Allow roots to be injected for tests. Do not implement plugin package discovery.

Support portable `skills/<name>/SKILL.md`-style directories. Discover catalog metadata by reading only a bounded frontmatter/metadata prefix rather than every full body. Understand at least stable `name` and `description`, plus optional simple help/argument-hint metadata when present. Ignore unknown noncritical metadata safely. Prefer a small dependency-free parser for the required portable subset unless a concrete fixture proves a focused dependency is necessary.

Use stable qualified identities such as `builtin:<name>`, `user:<name>`, and `workspace:<name>`. Discovery order must be deterministic. An unqualified name resolves only when exactly one discovered skill owns it; ambiguity fails visibly instead of silently overriding by source precedence.

Validate names/paths and fail or skip with explicit diagnostics for malformed metadata, missing body, duplicate qualified identity, path/symlink escape, and bounded metadata/body violations.

Catalog discovery must not read every full skill body. Load a full body only when explicitly activated.

Expose presentation-independent application/core APIs to list compact skill metadata, resolve a skill identity, and activate one or more skills for a submitted user turn.

Activated skill bodies enter the existing context trust/precedence/budget machinery, remain active across that turn's provider/tool rounds, and drop out on the next unrelated turn unless explicitly activated again. Persist/diagnose skill identity, not the full body.

Skill text is model-facing guidance only: it cannot register executors, change permission classes, bypass approvals, widen filesystem scope, expose secrets, or enable network access.

Do not implement automatic semantic skill routing, executable hooks, plugin manifests, or generalized user commands.

Set `package.json` version to `0.3.3`.

Required proof:
- discovery tests cover built-in/user/workspace sources, stable order, qualified identities, unique unqualified resolution, and collisions;
- malformed/missing/oversized/path-escape cases are explicit;
- catalog tests prove full bodies are not eagerly loaded;
- activation tests prove full body is loaded just in time, survives the current multi-round turn, and is absent from the next unrelated turn;
- context-budget exhaustion for an activated skill is explicit;
- at least one fixture is a portable external-style `SKILL.md`, not a George-specific format;
- malicious skill text cannot raise executable authority;
- existing context/tool/provider/TUI tests remain Green;
- typecheck, broad deterministic tests, `git diff --check`, and no-`package-lock.json` checks pass.

Stop with `Planning needed` if portable compatibility requires freezing a Phase-5 plugin manifest or executable extension semantics.
